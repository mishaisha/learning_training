Route 53:
- A highly available, scalable, fully managed Authoritative DNS
- Its also a Domain Registrar
- The only AWS service with 100% SLA

Route 53 record:
Each record contain Domain name, Record Type ( A/AAAA/CNAME/NS), Value, Routing Policy, TTL

A - maps hostname to IPv4
AAAA - maps hostname to IPv6
CNAME - maps hostname to another hostname
NS - Name Servers for the Hosted Zone

Public Hosted Zone - public domain names
Private Hosted Zone - private domain names

TTL:
- This is the time the Client will cache the result for the TTL record
- High TTL : less traffic on Route 53, oudated records
- Low TTL: More traffic on Route 53, records are outdated for less records
- is mandatoery for every record except Alias records

CNAME Vs Alias:
CNAME 
- points a hostname to any other hostname
- only for non root domain
Alias:
- points a hostname to an AWS Resource (ELB, CloudFront, API Gateway, Beanstalk, S3)
- Works for root domain and non root domains
- Unlike CNAME, it can be used for the top node of a DNS namespace
- Alias Record is always of type A/AAAA
- You cant set the TTL
- You can't set an ALIAS record for an EC2 DNS name

Routing Policy:
Simple:
- Route traffic to a single resource
- No health checks

Weighted
- Control the % of the requests that go to each specific resource
- If weight is 0, Route 53 will stop sending requests to that resource

Latency
- Route traffic to the resource that has least latency close to the user

Failover:
- One primary and secondary
- Mandataory health check to primary instance

Geolocation:
- This is based on user location
- Must create a "Default" record

Geoproximity:
- This is based on user location and resources
- shift traffic to resources based on Bias
	- To expand (1-99) - more traffic to the resource
	- To shrink (-1 to -99) - less traffic to the resource

Multi-Value:
- Use when rerouting traffic to multiple resources
- Route 53 returns multiple values

Health Checks:
- HTTP health checks are only for public resources
Private Hosted Zones:
- Create a CloudWatch Metric and associate a CloudWatch Alarm. Create a health check that checks the alarm itself

DynamoDB:
- NoSQL serverless DB, fully managed
- Replication across multiple AZs
- Maximum size of each item (row) - 400KB
- Each item will have attributes (columns)

Primary Key:
Partition Key (HASH) - example: user_id

Read/Write Capacity Modes:
Provisioned Mode (default)
- We need to specify the number of reads/writes per second
- Need to plan capacity beforehand
- Pay for provisioned read & write capacity units
- Throughput can be exceeded temporarily using "Burst Capacity"
- If Burst capacity has been consumed, throws an exception "ProvisionedThroughputExceededException"

WCU: (Write Capacity Units)
- One WCU represents one write per second for an item up to 1 KB size

Strongly Consitent Read Vs Eventually Consistent Read:

Eventually Consistent Read:
- If we read just after a write, its possible we'll get some stale data

Strongly Consistent Read:
- If we read just after a write, we'll get correct data

RCU:
- One RCU represents one Strongly Consistent Read per second or two Eventually Consitent Reads per second for an item upto 4 KB in size

WCUs and RCUs are spread evenly across partiions

Throttling:
- Use Exponential backoff

- Use DeleteTable to delete a whole table and all its items instead of DeleteItem

Local Secondary Index ( LSI):
- Alternate Sort Key
- Must be defined at the table creation time
- No special throttling considerations

Global Secondary Index ( GSI):
- Alternate Primary Key from the base table
- can be modified after table creation
- If the writes are throttled on the GSI, the main table will be throttled
- Global Secondary Index (GSI) uses an independent amount of RCU and WCU and if they are throttled due to insufficient capacity, then the main table will also be throttled.

On-Demand Mode:
- No need for capacity planning
- Read/Writes automatacilly scale up/downloaded
- More expensive, used for Unknown workloads

PartiQL:
- use SQL-like syntax

Optimistic Locking:
- A strategy to ensure an item hasn't changed before you update/delete it
- Its controlled through versioning
- ConditionalWrites allows us to achieve Optimistic Locking


DAX (Dynamo DB Accelerator)
- Fully managed in-memory cache
- Solves the "Hot Key" problem ( too many reads)
- 5 minutes TTL
- Multi AZ ( min 3 nodes recommended for Prod)

- DynamoDB Accelerator (DAX) is a fully managed, highly available, in-memory cache for DynamoDB that delivers up to 10x performance improvement. 
It caches the most frequently used data, thus offloading the heavy reads on hot keys of your DynamoDB table, 
hence preventing the "ProvisionedThroughputExceededException" exception.

DynamoDB Transactions:

- TransactWriteItems is a synchronous and idempotent write operation that groups up to 25 write actions in a single all-or-nothing operation. 
- The actions are completed atomically so that either all of them succeed or none of them succeeds.
- A TransactWriteItems operation differs from a BatchWriteItem operation in that all the actions it contains must be completed successfully, or no changes are made at all. 
- With a BatchWriteItem operation, it is possible that only some of the actions in the batch succeed while the others do not.
- Amazon DynamoDB" supports a maximum item size of 400 KB.

Capacity Computations:
Example: 3 Transactional writes per second, with item size 5 KB
WCU = 3 * (5/1) * 2 ( transactional cost) = 30 WCUs
Example: 5 Transactional reads per second, with item size 5 KB
RCU = 5 * (8/4) * 2 ( transactional cost) = 20 RCUs
NOTE: ( 5 gets rounded to upper 4 KB, in this case it gets rounded to 8 KB)

MessageVisibilityTimeout:
